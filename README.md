# МТ9 — сайт кафедры и админка

React-сайт с управлением материалами без изменения кода. Frontend (nginx), backend
(Flask + SQLite) и планировщик резервного копирования работают в отдельных Docker-контейнерах.
На сервере нужны Git, Docker Engine и Docker Compose v2 с поддержкой `up --wait`.

## Быстрый запуск

```bash
git clone https://github.com/BerMemLeak/mt_9_site.git
cd mt_9_site
git checkout feat/admin-docker-backups
./scripts/start.sh
```

Скрипт создаёт `.env` со случайными паролем администратора и служебными ключами,
собирает образы и ждёт готовности сервисов. При повторном запуске `.env` не меняется.
Сайт: `http://<адрес-сервера>:8080`, админка: `/admin`.
Логин — `admin`, пароль — значение `ADMIN_PASSWORD` в локальном `.env`.
Не публикуйте этот файл. Порт можно изменить через `SITE_PORT`.

Если `.env` создаётся вручную, используйте `.env.example` как описание полей и
задайте собственные случайные значения. Backend откажется запускаться с короткими
ключами или паролем короче 12 символов.

Для публикации на домене настройте HTTPS на внешнем reverse proxy и задайте
`COOKIE_SECURE=true` в `.env`, затем повторите запуск. При проксировании перед
nginx сохраните лимиты и таймауты загрузки больших файлов. HTTP подходит для
локальной проверки; перед входом в публичную админку настройте HTTPS.

## Управление материалами

В админке доступны анонсы, новости, преподаватели, проекты, образование,
дисциплины, расписания, документы, основные страницы и курсы. Есть поиск,
форматирование текста, загрузка и выбор файлов, предпросмотр текста,
черновики, публикация и архив. После сохранения опубликованные изменения
появляются при следующей загрузке страницы сайта, без пересборки контейнеров.

Материалы старой версии перенесены в `backend/seed.json`: 14 анонсов, 2 новости,
17 преподавателей, 2 проекта, сведения об образовании, 5 дисциплин, 6 расписаний,
5 групп документов, 4 страницы и 5 курсов. Начальные данные загружаются только
при создании пустого хранилища. Обновление приложения не перезаписывает редактуру.
Дубли и старые даты оставлены намеренно, чтобы сохранить исходные материалы.
Исходные JS-файлы оставлены для истории; сайт получает актуальные данные из API.

Локальные исторические фотографии при первом запуске копируются в хранилище
загрузок и входят в бэкап. Для внешних файлов откройте **Файлы → Перенести старые
файлы на сервер**. Импорт скопирует доступные картинки и документы с исходных
сайтов университета и заменит ссылки. Недоступные адреса сохраняются, а ошибки
показываются в админке. Исходно отсутствующие DOCX/XLSX и неверные ссылки не
восстанавливаются из воздуха: загрузите правильные файлы через редактор.
Во время импорта не редактируйте материалы; конфликтующие разделы не
перезаписываются, и их можно обработать повторно. После импорта создайте копию.

Один файл может иметь размер до **2 ГиБ (2147483648 байт)**. Загрузка идёт на диск,
а не целиком в память. Для файлов вне изображений/аудио/видео используется
скачивание вложением. Удаление записи не удаляет файл физически: он мог
использоваться в других материалах. Все загруженные файлы публичны.

## Резервные копии и восстановление

Планировщик проверяет срок каждый час. Первая копия создаётся при запуске,
следующая — не раньше чем через семь суток после последней успешной
автоматической копии. Простой сервера не сбрасывает срок: после запуска
просроченная копия создаётся при ближайшей проверке. Ошибки приводят к повторной
попытке через час и видны в админке и журнале backend.

Один ZIP64-архив содержит согласованный снимок SQLite, **все загруженные файлы**
и манифест с SHA-256. ZIP хранится без дополнительного сжатия: большие видео
и архивы обычно уже сжаты. Копии хранятся **два календарных месяца**; старые
автоматически удаляются только после успешного создания новой копии.

В разделе **Резервные копии** можно создать копию вручную, скачать её или
загрузить для восстановления. Восстановление:

1. Проверяет формат, пути, размер, контрольные суммы, целостность и версию БД.
2. Разворачивает данные в отдельной временной папке.
3. Создаёт контрольную копию текущего состояния.
4. Атомарно переключает базу и папку загрузок вместе. При ошибке до переключения
   прежние данные остаются доступны.

Сначала подтвердите замену данных флажком, затем загрузите архив. Состояние
операции отображается в админке; вкладку можно закрыть, обработка продолжится.
Логин, пароль и ключи из `.env` в архив **не входят** и при восстановлении
не меняются. Так копия контента переносится на новый сервер с новым паролем.
Архив не объединяет записи, а заменяет содержимое сайта целиком.

Архив целого сайта может быть больше 2 ГБ. Для него отдельный лимит — 100 ГиБ
по умолчанию (`MAX_BACKUP_BYTES`); лимит загрузки одного материала остаётся 2 ГиБ.
Для передачи больших файлов и архивов в nginx и gunicorn заданы таймауты 2 часа.
Создание и распаковка выполняются в фоне. Одновременно идёт только одна операция
копирования, восстановления или импорта старых материалов.

Нужен запас места для текущих файлов, примерно девяти полных еженедельных копий,
временного архива и распакованной копии. При восстановлении также создаётся
контрольная копия. Предыдущее поколение файлов сохраняется до следующего запуска
backend, чтобы не обрывать уже начатые скачивания.

**Копия на том же сервере не защищает от потери диска.** Скачивайте архивы
в отдельное место. Автоматическое внешнее хранилище пока не настроено.

Для восстановления на новом сервере: запустите приложение, войдите с его новым
паролем, загрузите ZIP в админку и дождитесь завершения. Настройки домена, HTTPS
и `.env` хранятся отдельно от контента и настраиваются на новом сервере заново.

## Обновление, остановка и диагностика

```bash
git pull --ff-only
./scripts/start.sh
docker compose ps
docker compose logs --tail=100 backend scheduler
./scripts/stop.sh
```

Обычные `docker compose down` и пересборка сохраняют named volume `site_data`.
**`docker compose down -v` удалит данные и копии** — не используйте для обновления.
Backend наружу не опубликован; API и файлы доступны через nginx. Внутренний
endpoint планировщика закрыт во внешнем nginx и защищён отдельным токеном.
Сайт больше не раздаёт папку репозитория.

## Разработка и проверки

```bash
npm ci
CI=true npm run build
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt pytest
.venv/bin/pytest -q backend
npx playwright install --with-deps chromium
PYTHON=.venv/bin/python npm run test:ui
```

UI smoke использует временную БД и локальные порты 8000/8080. Проверяет вход,
публикацию, все основные публичные маршруты, загрузку файла, создание копии и
мобильную ширину. Backend-тесты проверяют авторизацию/CSRF, лимиты, скрытие
черновиков, защиту HTML, восстановление на пустом сервере, повреждённые архивы,
небезопасные пути, еженедельный срок и удаление старых копий.

Миграция начального содержимого воспроизводится командой
`node scripts/export-legacy.cjs` из исходного коммита `5f9d57f`; она изменяет
только seed и исторические изображения, а не данные работающего сайта.

Production backend запускается **в одном gunicorn worker с потоками**: фоновые
операции координируются внутри процесса. Не увеличивайте число worker/реплик
без перехода на отдельную очередь заданий и межпроцессную координацию.
